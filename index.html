GenAI · RAG Pipeline · LLM Application

RAG Document Q&A System — Full-Stack LLM Application

Built an end-to-end Retrieval-Augmented Generation pipeline with token-aware chunking (256-token limit) and FAISS vector search (cosine similarity), returning source citations with every answer. Served via a FastAPI backend (3 REST endpoints, Pydantic validation) with a two-layer no-answer guard that suppresses hallucination on out-of-context queries. Logged queries to SQLite with a usage-analytics endpoint and a Streamlit chat dashboard, validated across 30+ test queries.

256-token chunking 3 REST endpoints 30+ test queries
PythonFastAPIFAISS Sentence-TransformersLLM (Groq)SQLiteStreamlit
GitHub Jun 2026
Problem

Most document Q&A demos are notebook prototypes that hallucinate confidently on questions outside their source material. The goal was a full-stack RAG application that answers strictly from a document corpus, cites its sources, and explicitly declines to answer when the context doesn't support a confident response.

Challenges

Balancing chunk size against retrieval precision — chunks too large dilute relevance, too small lose context. A two-layer no-answer guard (retrieval-confidence check plus an LLM-level refusal path) was needed to stop the model from hallucinating plausible-sounding answers on out-of-context queries.

Process

Document ingestion → token-aware chunking (256-token limit) → embedding (Sentence-Transformers) → FAISS vector index (cosine similarity) → FastAPI serving layer (3 endpoints, Pydantic validation) → two-layer no-answer guard → SQLite query logging → Streamlit chat dashboard

Key Insight

The two-layer no-answer guard — a retrieval-confidence threshold combined with an explicit LLM-level refusal path — suppressed hallucination more reliably than prompt engineering alone; source citations on every answer made responses independently verifiable rather than requiring trust in the model.

Value

End-to-end RAG pipeline with citation-backed answers · FastAPI backend with 3 REST endpoints and Pydantic validation · Two-layer no-answer guard suppressing hallucination · Usage-analytics endpoint tracking frequency, no-answer rate, and latency · Validated across 30+ test queries.

Supply Chain · Statistical Modelling · Dashboard

Supply Chain & Shipping Analytics – Nassau Candy Distributor

Analysed 8,549 shipments across 5 factories, 4 regions, and 4 shipping modes; ranked all 16 factory-to-region routes by composite efficiency score (lead time + delivery variability). Disproved the assumed speed premium of Same Day shipping via hypothesis testing (p > 0.05), surfacing a data-backed case to eliminate the ~30% cost premium on expedited orders.

8,549 shipments 16 routes ranked 5 factories · 4 regions
PythonPandasSciPy NumPyPlotlyStreamlit
Live App GitHub Mar – Apr 2026
Problem

A distributor shipping confectionery products from 5 factories across multiple regions needed to know which factory→region routes were genuinely efficient and which were bottlenecks — and whether Same Day shipping actually delivered faster than Standard Class in practice.

Challenges

Applying the same confidence interval logic to a route with 19 shipments as one with 1,500+ produces misleading rankings. A custom Z vs t-distribution framework was built to handle variable sample sizes correctly, with thresholds set from the actual percentile distribution of the data — not hardcoded arbitrarily.

Process

Data cleaning (corrupted dates, cart-update duplicates, misclassifications) → Three-way merge (orders + products + factories) → Percentile analysis → Custom Z vs t-distribution confidence framework → Composite efficiency score (lead time + delivery variability) → 16 route rankings → Hypothesis testing (Same Day vs Standard Class) → Streamlit dashboard

Key Insight

Hypothesis testing confirmed no significant difference in delivery time between Same Day and Standard Class (13.3 vs 13.1 days, p > 0.05) — disproving the assumed speed premium and making a data-backed case to eliminate the ~30% cost premium on expedited orders.

Value

8,549 shipments analysed · 16 factory→region routes ranked by composite efficiency · Same Day shipping speed premium disproved (p > 0.05) · ~30% cost premium on expedited orders flagged as eliminable · Statistically rigorous confidence framework with automatic Z vs t selection · Fully interactive Streamlit dashboard.

Healthcare Capacity Analytics · Time-Series · Dashboard

System Capacity & Care Load Analytics for Unaccompanied Children

Analysed 720 daily CBP–HHS operational reports (Jan 2023 – Dec 2025) to build a structured capacity-monitoring framework for the federal Unaccompanied Children care pipeline. Derived 4 core capacity metrics and 5 stakeholder KPIs, then applied rolling-window analysis to flag sustained strain and relief periods. Combined system load fell from a peak of ~11,760 children in December 2023 to under 2,100 by August 2025, tracked in a live Streamlit monitoring dashboard.

720 daily reports ~71% load decline 5 KPIs delivered
PythonPandasNumPy Time-Series AnalysisRolling-Window AnalysisStreamlit
Live App GitHub Dec 2025 – Jan 2026
Problem

Daily operational data flows across the CBP–HHS Unaccompanied Children care pipeline, but there was no centralised analytical framework to continuously assess total system load, the balance between inflow and outflow, or when the system was under sustained strain versus relief — leaving capacity decisions reactive rather than proactive.

Challenges

Reporting cadence isn't a strict daily feed — Friday and Saturday reports are almost never published, a structural artifact of the source cycle rather than missing data. Rolling-window calculations had to operate on report sequence rather than naive calendar days to avoid distorting the strain/relief signal. Two logical constraints (transfers ≤ same-day custody, discharges ≤ same-day care) were tested directly against the data rather than assumed.

Process

Data ingestion & cleaning (720 reports, thousands-separator parsing, calendar indexing) → constraint validation (transfer/discharge logic checks) → 4 derived capacity metrics (Total System Load, Net Daily Intake, Growth Rate, Cumulative Backlog) → rolling 7- and 14-report averages → percentile-based strain/relief window detection → 5 stakeholder KPIs → Streamlit monitoring dashboard

Key Insight

A 7-report rolling average crossing into the historical top or bottom quartile, sustained for 10+ consecutive reports, cleanly separated genuine strain/relief periods from day-to-day noise — identifying one dominant 111-report strain window (Aug 2023–Jan 2024) and an ongoing 117-report relief window (Jun–Dec 2025) that a simple day-over-day view would have missed.

Value

4 capacity metrics and 5 KPIs delivered from 720 daily reports · Combined system load decline of ~71% quantified (2023 average → 2025 average) · Sustained strain and relief windows identified via percentile-based rolling analysis · Discharge Offset Ratio tracked as an early-warning backlog indicator · Live Streamlit dashboard for ongoing monitoring.

Problem

Most forecasting projects end at a Jupyter notebook; a trained model that lives on someone's laptop and gets manually re-run. The goal here was to build a system; something production-ready, modular, and deployable by anyone with a single command.

Challenges

Getting the pipeline architecture right so each component has a single responsibility. The temptation is to couple the model and the serving layer — it's simpler to build. Predictive Modelling · Profit Optimisation · Dashboard

Restaurant Profit Optimisation — SkyCity Auckland

Built and evaluated 4 models (Linear Regression, Random Forest, Gradient Boosting, XGBoost) to forecast restaurant profit from channel mix and commission structure across 1,696 restaurants; XGBoost explained 98.8% of profit variance (MAE $464). Built a scenario simulator and grid-search optimisation layer into a live Streamlit dashboard, identifying a median 21.7% profit uplift achievable through channel-mix rebalancing alone, and derived a 32.6% break-even commission benchmark showing ~29% of restaurants losing money on aggregator orders at current rates.

98.8% variance explained 21.7% median profit uplift 1,696 restaurants
PythonXGBoostScikit-learn StreamlitGrid Search
Live App GitHub May – Jun 2025
Problem

Restaurants selling through third-party aggregators pay a commission on every order, but have no easy way to know whether their current channel mix (direct vs. aggregator) is actually profitable, or what mix would maximise profit given their specific cost structure. The goal was a tool that predicts profit from channel mix and commission terms, and recommends a better mix.

Challenges

Choosing the right model meant balancing accuracy against interpretability for a business audience — a black-box model with no way to simulate “what if 10% of orders shifted to direct” wouldn't be actionable. Building a grid-search optimisation layer on top of the trained model, rather than just a static prediction, was necessary to turn a forecasting exercise into a decision-support tool.

Process

Data cleaning & feature preparation (channel mix, commission structure) → model benchmarking (Linear Regression, Random Forest, Gradient Boosting, XGBoost) → XGBoost selected (98.8% variance explained, MAE $464) → grid-search optimisation layer for channel-mix rebalancing → break-even commission benchmarking → Streamlit scenario simulator dashboard

Key Insight

A 32.6% break-even commission benchmark revealed that roughly 29% of restaurants in the dataset were losing money on aggregator orders at their current commission rates — a concrete, model-derived negotiation lever that channel-mix intuition alone wouldn't have surfaced. Rebalancing channel mix alone, without any pricing change, produced a median 21.7% profit uplift.

Value

4 models benchmarked, XGBoost selected at 98.8% variance explained (MAE $464) · Median 21.7% profit uplift identified through channel-mix rebalancing · 32.6% break-even commission benchmark derived · ~29% of restaurants flagged as unprofitable on aggregator orders at current rates · Live Streamlit scenario simulator with grid-search optimisation.

MSc Dissertation · Deep Learning · Research

5G Energy Consumption Prediction

MSc dissertation; built hybrid CNN-RNN models (LSTM, GRU) to forecast hourly energy consumption across 1,020 5G base stations on 92,629 records. Achieved 44% reduction in forecast error (MAE: 1.52 → 0.85, MAPE: 3.3%) with consistent performance on unseen stations using group-stratified cross-validation.

44% MAE reduction MAPE: 3.3% 1,020 base stations
PythonPyTorchCNN-RNN / LSTM / GRU Feature EngineeringOptunaGroup-Stratified CV
GitHub Feb – Jul 2025
Problem

5G network infrastructure consumes significantly more energy than previous generations. Operators need to predict consumption patterns across base stations; both to manage costs and to identify efficiency opportunities. The dissertation asked: can we accurately forecast energy consumption at the base station level, generalising to unseen stations?

Challenges

The data leakage problem. In a dataset with 1,020 base stations, naïve cross-validation would train on observations from the same station it tests on; producing optimistic results that don't reflect real-world deployment. Solving this correctly — using group-stratified cross-validation — was the difference between publishable results and inflated ones.

Process

Data exploration (92,629 records, 1,020 stations) → Feature engineering (20+ features: temporal lags, spline time encodings, signal smoothing filters) → Baseline modelling → Hybrid CNN-RNN (LSTM, GRU) architecture → Optuna TPE hyperparameter tuning → Group-stratified cross-validation (no station overlap)

Key Insight

Engineering 20+ features — temporal lags, spline time encodings, and signal smoothing filters — contributed more than model complexity. Group-stratified cross-validation is the correct validation strategy for grouped time-series data; it ensures the model genuinely generalises to unseen base stations rather than memorising known ones.

Value

44% MAE reduction (MAE: 1.52 → 0.85, MAPE: 3.3%) · Consistent performance on unseen base stations via group-stratified CV · 20+ engineered features · 92,629 records across 1,020 stations. Dissertation-grade rigour; results are defensible, not just impressive-looking.
